# Migrate an evidence Bundle from 0.1 to 0.2

Migration is explicit. Loading, validating, or rendering a 0.1 artifact never
rewrites it. During the compatibility window, the validator and renderer accept
both versions; new applications should migrate once and retain both artifacts.

```bash
git-evidence migrate legacy-bundle.json --output bundle-0.2.json
git-evidence validate bundle-0.2.json
```

The migrated Bundle records the SHA-256 digest of the exact source file bytes,
the migration time, and a new invocation identity. Its `plan.origin` is
`legacy_migration`: the original 0.1 artifact did not retain every normalized
configuration option required to reconstruct a live collection plan, so the
migration does not invent those values.

The migration performs these breaking contract changes:

- `run.run_id` becomes a recomputable `plan_id` plus a random invocation ID;
- the exact canonical 0.2 content receives a recomputable `bundle_digest`;
- `facts` become typed `assertions`; free-text summaries and presentation
  sections are not copied into the canonical claim protocol;
- Evidence references an explicit `legacy_import` Retrieval; its
  `native_identity` is explicitly `unavailable` because 0.1 did not retain a
  separately typed native object identity;
- `coverage.allow_publish` becomes `coverage.render_eligible` and retains only
  its render-gate meaning;
- unknown fields are rejected unless they are contained under a
  provider-namespaced `extensions` object.

Migration refuses an invalid 0.1 source. A changed `plan_id`, `bundle_digest`,
or source artifact digest is a new artifact identity, not a cosmetic rewrite.
